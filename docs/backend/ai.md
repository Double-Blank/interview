# AI 加试

## 十二、结合 AI 全栈岗位的加试题（20 题）

### 1. Java 与 Node.js 后端对比

#### 1. Java 和 Node.js 分别适合什么业务场景？

Java 适合长生命周期的业务服务：复杂事务、强类型约束、大量并发下的稳定 CPU 与线程模型、已有 Spring 生态的企业系统。计算和业务流程混在一起、要长期维护时，Java 的类型和线程池比较好控制。

Node.js 适合 I/O 密集、和前端同语言的 BFF、实时网关、AI Agent 编排。JSON 接口、流式输出和 JavaScript 生态的模型 SDK 接起来快。CPU 很重的任务不适合堵在 Node 的主线程里，应拆出去。

一个系统里两者可以共存：Java 管用户、订单和权限，Node 管面向模型和前端的编排。

#### 2. Java Spring Boot 和 NestJS 在架构设计上有什么相似之处？

两者都强调模块化和依赖注入。NestJS 的 Module、Controller、Provider，对应 Spring 的配置与组件扫描、Controller、Service Bean。

请求都是先进控制器，再进服务层。横切能力都用声明式方式：Nest 的 Guard、Interceptor、Pipe，对应 Spring 的过滤器、拦截器和 Validation。配置都支持按环境区分。所以 Nest 项目迁到 Spring，可以按业务模块原样映射，不必重新发明分层。

#### 3. Spring Boot 的依赖注入和 NestJS 的依赖注入有什么区别？

思路相同：类声明自己需要的依赖，容器负责创建和注入，业务代码不自己 `new`。

Spring 默认单例，主要按类型注入，同类型多个时用名字或 `@Qualifier`。Bean 可以来自组件扫描或 `@Bean` 方法。NestJS 也是构造器注入，Provider 注册在模块里，默认同样是单例作用域，还可以声明请求作用域。

Spring 的循环依赖在字段注入时能靠三级缓存创建成功。Nest 默认不鼓励这种循环，应拆模块。Spring 的 AOP 代理和 Nest 的装饰器都可能让“类内部自己调用自己”不走增强，这一点两边都要小心。

#### 4. Java 和 TypeScript 的类型系统有什么区别？

Java 的类型在编译后仍有运行时类信息。泛型会被擦除，但对象本身知道自己的类。类型不匹配过不了编译，强转失败在运行时抛异常。

TypeScript 的类型只存在于编译期，编译成 JavaScript 后就没了。接口、类型别名不会在运行时留下结构，所以运行时仍要校验外部 JSON。`any` 可以绕过类型系统。

Java 用类和接口描述数据，DTO 是真对象。TypeScript 更常用结构类型：只要形状匹配就能赋值，名义上是不是同一个类不重要。和外部系统交换数据时，两边都要在边界做校验，不能假设类型标注等于运行时安全。

#### 5. Java 的线程模型和 Node.js 的事件循环模型有什么区别？

Java 用操作系统线程处理并发。一个请求可以占用一个线程直到数据库或 HTTP 返回。线程有栈，数量太多会占内存，所以用线程池限制并发，并靠多线程利用多个 CPU。

Node.js 主线程是单线程事件循环。请求到来后注册回调，等待数据库和网络时不占用主线程，结果回来再继续执行。CPU 密集计算会堵住事件循环，所有请求一起变慢。

Java 的并发问题主要是共享内存和锁。Node 的并发问题主要是不要阻塞事件循环，以及回调或 Promise 链里的错误处理。Java 21 的虚拟线程缩小了这两种模型在“大量阻塞 IO”上的差距。

#### 6. Node.js 为什么可以处理大量 I/O 密集型请求？

大多数时间花在等网络和磁盘，而不是算。Node 发起 IO 后把回调交给系统，主线程回去处理别的请求。一个线程就能挂住很多未完成的连接，内存比“一请求一线程”小。

前提是 IO 使用非阻塞 API。如果在主线程里做大循环、同步加密或同步读大文件，事件循环停住，并发优势就没了。这类工作应放到 worker 或独立服务。

#### 7. Java 如何处理高并发请求？

Tomcat 用线程池接收请求，每个请求在一个线程里执行。线程数和数据库连接池要匹配，不能线程很多、连接很少，否则请求都堵在等连接上。

读多的数据放缓存。写请求缩短事务，热点行避免频繁锁冲突。入口限流，下游调用设置超时。服务无状态，才能加实例。CPU 密集任务用独立线程池，不要占用 Web 容器线程。JDK 21 可以用虚拟线程承载大量阻塞调用，载体线程仍由 JVM 调度到少量操作系统线程上。

#### 8. Java 后端和 Node.js 后端如何通过 HTTP 通信？

把对方当成外部服务，走 HTTP 或内部 RPC，不共享进程和数据库连接。Java 用 `RestClient` 或 OpenFeign 调用 Node 的接口；Node 用 `fetch` 调用 Java。

合同用 OpenAPI 固定路径、字段和时间格式。内部调用要带超时、重试和 traceId。认证用内部 token 或 mTLS，不要假设内网就没有伪造请求。同步调用链路不要太长。模型这种慢调用改成异步任务或流式响应，避免 Java 线程一直等着 Node。

#### 9. Java 和 Node.js 如何共享统一的数据结构？

运行时不能共用一个类。共享的是接口合同：同一套 JSON 字段、枚举值和错误码。用 OpenAPI 或 JSON Schema 做源头，再生成 Java record 和 TypeScript 类型，避免两边各写一份后慢慢不一致。

字段用明确的名字和单位。时间统一 ISO-8601 或统一毫秒时间戳，金额用最小货币单位的整数。可选字段约定是省略还是 null。合同变更先加字段，再让旧字段退出。

#### 10. 什么情况下会选择 Java 作为 AI 应用的后端服务？

模型编排可以放在 Node 或 Python，但用户、权限、审计、计费、限流这些要进企业现有系统时，用 Java 更合适。团队已经有 Spring 的发布、监控和数据库规范，也适合把 AI 接口做进同一个服务。

Java 负责鉴权、保存对话、控制配额和调用模型网关。模型推理和向量检索如果已有 Python 服务，Java 通过 HTTP 调用，不把推理硬塞进业务进程。需要稳定事务和长期维护的 AI 业务后端，选 Java；快速拼 Agent 原型，可以继续用 Node。

### 2. AI 应用后端

#### 11. 如何设计一个大模型调用接口？

业务接口不要把供应商的请求格式直接暴露给前端。例如 `POST /conversations/{id}/messages`，请求体是用户输入和会话 id，响应是助手回复。

Service 里做这些事：校验登录和配额，取出最近的上下文，拼成模型需要的 messages，调用模型客户端，把回复和 token 用量写入数据库，再返回给前端。供应商地址和模型名放配置。客户端统一设置超时，并把供应商错误转换成自己的业务异常，例如配额用尽、内容被拒绝、上游超时。密钥只放在服务端。

#### 12. 如何设计一个支持流式输出的 SSE 接口？

模型输出是一段段 token，适合用 SSE 单向推给浏览器。接口返回 `Content-Type: text/event-stream`，Controller 使用 `SseEmitter`，不要等全部生成完再返回。

```java
@GetMapping(value = "/conversations/{id}/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter stream(@PathVariable Long id) {
    SseEmitter emitter = new SseEmitter(120_000L);
    streamExecutor.execute(() -> modelClient.stream(id, emitter));
    return emitter;
}
```

工作线程每收到一段就 `emitter.send`。正常结束发送一个完成事件并 `complete`。失败时 `completeWithError`，前端按事件类型停止加载。Emitter 设超时，客户端断开要停止向上游读取，避免白跑 token。Nginx 需要关闭这段响应的缓冲。

#### 13. SSE 和 WebSocket 有什么区别？

SSE 基于 HTTP，服务器单向往客户端推文本事件。浏览器有 `EventSource`，自动重连，实现简单。它沿用现有的 HTTP 认证和网关，适合模型流式输出、任务进度。

WebSocket 是双向长连接，客户端和服务器都能随时发消息，适合聊天室、协同编辑。它要单独处理心跳、重连和负载均衡。

模型回答只需要服务器不断把 token 推下来，用 SSE 就够。如果用户要在同一条连接里随时插入新指令、打断生成，再用 WebSocket。

#### 14. 如何处理大模型接口超时？

超时要分开设。连接超时短一些，例如几秒，发现地址不可达就失败。读取超时按场景给，流式接口可以较长，但必须有上限。不能使用无限等待。

超时后释放线程和连接，返回明确错误，让用户重试。已经开始流式输出又中断时，把已生成的内容保存下来并标记未完成。重试前先确认这次调用是否可能已经在供应商侧计费，避免盲目立即重试多次。慢调用不要放在数据库事务里面。

#### 15. 如何处理大模型 API 的限流？

供应商会返回 429，自己的服务也要在到供应商之前做限制。按用户和按接口两个维度限流，防止一个用户把配额打光。

收到 429 时读取 `Retry-After`，等待后再试，或者把请求放进队列。并发数用信号量封顶，超过的请求排队或直接拒绝。业务上记录每分钟 token 用量，接近配额时提前拒绝，比打到供应商再失败更可控。限流错误返回 429，并告诉前端稍后重试。

#### 16. 如何实现大模型调用失败后的重试机制？

只重试短暂失败：连接重置、502、503、429。参数错误、认证失败、内容审核拒绝不能重试，重试也一定会失败。

重试次数限制在 2 到 3 次，使用指数退避加随机抖动，避免所有请求同一秒再打过去。每次调用带同一个幂等键，重试不会在自己的数据库里插入多条用户消息。流式输出一旦已经往前端写了内容，就不能无声地整段重来，应把失败状态告诉前端。用 Resilience4j 可以统一描述这些策略。

#### 17. 如何设计 AI 对话历史记录的数据表？

至少两张表。

会话表 `conversation`：`id`、`user_id`、`title`、`model`、`create_time`、`update_time`。

消息表 `message`：`id`、`conversation_id`、`role`（system、user、assistant）、`content`、`token_count`、`status`、`create_time`。`conversation_id + create_time` 或自增 id 保证顺序。

超长回复可以只在消息表存文本。如果要审计原始请求，另存一张调用记录：供应商、模型、请求 id、耗时、是否失败，不和展示用的消息混在一起。内容可能含个人信息，权限上只能由会话所有者读取。

#### 18. 如何实现 AI 对话的上下文管理？

模型是无状态的，上下文要由后端每次带上。从消息表按时间取出当前会话的历史，拼成 messages 列表，再加最新的用户输入。

历史会超过模型上下文窗口。可以只保留最近 N 轮，或把更早的对话总结成一段系统消息。系统提示词放在最前，并且不要让用户消息覆盖它。token 数量在调用前估算，超限先裁剪历史，而不是等供应商拒绝。

用户删除会话时，后续请求不再带这些消息。多实例部署时，上下文存在数据库或 Redis，不存在某台机器的内存里。

#### 19. 如何设计一个 RAG 知识库的后端接口？

分成文档管理和问答两条线。

文档：`POST /knowledge-bases/{id}/documents` 上传文件，异步做解析、切片、向量化，任务状态可查询。删除文档时同时删向量。查询接口只访问当前用户有权限的知识库。

问答：`POST /knowledge-bases/{id}/queries`。后端把问题向量化，在该知识库里检索 Top K 片段，把片段和问题一起交给模型，返回答案和引用到的文档片段。检索为空时明确说没有依据，不让模型编。

向量库可以是独立服务。Java 负责权限、任务状态和引用结果，切片与嵌入可以由 Python 服务做。

#### 20. Java 如何调用 Python 或 Node.js 编写的 AI 服务？

通过 HTTP 调用，服务之间只共享 API，不把 Python 进程嵌进 JVM。Java 侧写一个客户端，例如 `AiClient`，里面固定 URL、超时、认证头和响应转换。业务 Service 依赖这个接口，测试时可以替换成假实现。

同步问答用普通 POST。流式用 SSE，Java 边读边转发给前端。耗时的索引任务用异步：Java 创建任务，Python 完成后回调，或者 Java 轮询任务状态。双方用同一个 traceId。Python 服务挂了，Java 返回 502 或 504，并有熔断，避免线程全部堵在下游。合同用 OpenAPI 固定，字段变化先改合同再改两边代码。
